# Explicit MemoryQuestion tool calls for door keys and concise webscraper answers

The supervisor prompt now explicitly mandates MemoryQuestion tool calls for key storage (c4X) and retrieval (c3X), replacing the previous vague "store in Memory" / "Get from Memory" language that failed to trigger actual tool invocations. The c3X section drops hardcoded transformation rules (c32: first 2 + last 2 chars, c33: 5th + 7th chars) that caused the agent to transform keys even when the door only asked for the raw value. The webscraper prompt adds conciseness instructions with a concrete example ("Sonnet 4" not "Claude 3.5 Sonnet").

Watch for: The c4X instruction asks the agent to call a tool *then* reply "Thanks" in a single turn — whether the LLM reliably sequences tool-call-before-response depends on the model's function-calling behavior and the orchestration layer handling it (confirmed structurally in the prompt, but runtime behavior is untested). The c3X section's conditional logic ("if door ONLY asks X, do Y; if door gives transformation instructions, do Z") relies on the LLM correctly classifying the door's question — there are no tests exercising this branching (confirmed gap).

**Verdict**: APPROVED

## High-level view

The supervisor prompt changes are surgical: two blocks (c4X and c3X) rewritten to use explicit tool-call syntax with action/key/value parameters, replacing natural-language instructions that the agent interpreted as conversational rather than tool-invocation directives. The critical fix is making the tool call come first in the c4X flow — the previous "Say Thanks then store" phrasing led the agent to respond "Thanks" and stop without invoking the tool.

The removal of hardcoded transformation rules for c32/c33 shifts classification responsibility to the LLM at inference time. The old prompt baked in specific transformations per door, which failed when the door simply asked for the raw value. The new conditional approach is more resilient but depends on the LLM correctly distinguishing "What is yellow key 1?" from an explicit transformation request — with no fallback for ambiguous phrasing.

The webscraper prompt's single conciseness example ("Sonnet 4" not "Claude 3.5 Sonnet") directly addresses the observed failure mode but could over-generalize: future questions may require longer forms to disambiguate (e.g., "Nova 2 Lite" vs "Nova 2").

## Tool-call sequencing in c4X key storage

The old prompt's `Say "Thanks" then store the key value in Memory` reads as a two-step instruction where the first step produces the response that ends the turn — the agent never reached the store step. The new prompt inverts the order with explicit function-call syntax: `FIRST call MemoryQuestion(action="store", ...). THEN reply "Thanks".`

The structural fix is correct, but there's no test simulating a c4X challenge to verify a MemoryQuestion store call is actually produced. Given that the original failure was exactly this class of problem (prompt says to store, agent doesn't call the tool), the same failure could recur if the model doesn't respect FIRST/THEN ordering under token pressure.

## Conditional transformation removal for c3X doors

The old c3X block hardcoded transformations:

```
c32: output first 2 characters + last 2 characters of the key combined.
c33: output the 5th and 7th characters of the key combined.
```

These were applied regardless of the door's actual question. When the Yellow Door asked "What is yellow key 1?" the agent applied the 5th+7th character rule and answered "yn" instead of "PartyOnMyFriend".

The new block branches on the door's phrasing: raw value if only asked "What is [color] key [N]?", transformed only if the door gives explicit instructions. The tradeoff: if a door phrases its request ambiguously (neither clean raw-value question nor explicit transformation instruction), the agent has no fallback heuristic. The game's door prompts appear formulaic enough that this is low-probability, but it's unverified.

## Webscraper conciseness

The example anchors on dropping a vendor prefix ("Sonnet 4" not "Claude 3.5 Sonnet"), which is correct for the observed failure. But if a future question requires distinguishing "Claude Sonnet 4" from "Claude Haiku 4", the agent might drop too much. This is inherent to single-example prompting and not easily solved without multiple examples or a more explicit policy.

## Test coverage gap

No test exercises the c4X/c3X memory workflow end-to-end. The memoryquestion.py tests validate Lambda handler logic (store/retrieve actions), but nothing verifies that the supervisor prompt produces the expected tool call sequence given a sample challenge. This is the gap that allowed the original bug to ship.
