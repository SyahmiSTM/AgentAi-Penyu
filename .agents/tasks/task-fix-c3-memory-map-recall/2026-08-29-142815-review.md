# Follow-up on the c3 map-recall fix: empty-vs-absent contract and jagged dimensions (v2)

The follow-up commit addresses all four issues from the v1 review of the c3 Memento map-recall fix. `_handle_count` now separates an absent `game_map` key (the recall case — fall back to the map remembered at game start) from an explicitly-passed empty map (`game_map == []`, a deliberate caller error that returns `Passed 'game_map' is empty`), and `lambda_handler`'s no-action backward-compat routing was flipped to dispatch on the *presence* of the `game_map` key so `_handle_count` owns that contract. `TestMemoryQuestion` gained a store-clearing `setUp`/`tearDown` so its pre-existing error test is self-isolating, a shared `_padded_dimensions()` helper makes `store_map` and `count` agree on rows/cols/total_cells for jagged maps, and the prompt-only anti-loop scope was documented in the CHANGELOG. Two new tests lock in the empty-passed-map contract and the jagged-dimension consistency.

Watch for: nothing blocking. **confirmed** — all four v1 issues are genuinely resolved and verified by execution; the empty-vs-absent split, the jagged-dimension helper, and test isolation all behave as intended. **possible** — the prompt-only anti-loop remains best-effort model compliance rather than a code guarantee, but this was reviewed in v1 and explicitly accepted as appropriate for the stateless-per-question Lambda.

**Verdict**: APPROVED

## High-level view

The empty-vs-absent contract is now explicit in one place. `_handle_count` branches on `'game_map' in body`: present-but-empty errors, absent recalls. The no-action routing in `lambda_handler` was changed from a truthiness check to a key-presence check so an empty-map no-action call reaches `_handle_count` and gets its descriptive empty-map error instead of the generic "Missing action" — a strictly clearer 400, and the real-map backward-compat path is unchanged.

Jagged-map dimensions are reconciled by measuring the padded rectangle in both paths. `_handle_store_map` computes `max(len(row))` on the raw map; `_handle_count` calls the same helper on the map after it has been padded to that same width. Both arrive at identical rows/cols/total_cells, and the counted answer is unaffected because padding uses `'normal'`.

Test isolation is fixed structurally: `TestMemoryQuestion` clears the shared store around every test, so `test_missing_game_map_error` no longer depends on another class running first. The anti-loop remains prompt-enforced by design, now documented in the CHANGELOG v10 entry.

The hard constraints hold: no `_handle_transform` / `_handle_store` / `_handle_retrieve` / `_TRANSFORM_RULES` lines changed, door/key/refusal/intake routing is untouched, and the `{statusCode, body: json.dumps(...)}` shape is preserved on every path.

### Empty-vs-absent now decided in `_handle_count`, routed on key presence

`_handle_count` reads the map as `if 'game_map' in body:` — a present key that is empty or not a list returns `Passed 'game_map' is empty: expected a non-empty list of rows`; an absent key recalls the remembered map and, if none exists, returns `No game_map available: none passed and none remembered from game start`. This is the deliberate contract the v1 review asked for: an empty passed map is a caller error even when a map is remembered, verified directly —

```
store_map([['c1','c1']]) then count(game_map=[], "how many c1?") -> {"error":"Passed 'game_map' is empty..."}
count(question=...) with a map remembered                        -> {"answer":"2", ...}
```

The paired routing change in `lambda_handler` matters for correctness: the no-action branch now tests `if 'game_map' in body and body.get('question')` instead of `if body.get('game_map') and ...`. Without the flip, a no-action call carrying `game_map: []` + a question would have fallen through to the generic `Missing 'action'` error; now it reaches `_handle_count` and gets the descriptive empty-map error. Both are 400s, so this is a clearer message rather than a behavior regression. A no-action call with a *real* map still routes to count exactly as before (confirmed by the unchanged backward-compat tests), and a map-only no-action call with no question still returns `Missing 'action'` — the presence check requires both keys, so nothing new leaks into the count path.

Auto-persist runs before the empty check and only fires on a non-empty list, so `game_map: []` never overwrites or clears a previously remembered map — the empty-passed-map test asserting the map is *still* remembered would break otherwise.

### `_padded_dimensions` reconciles jagged maps across both paths

The helper returns `(rows, cols, total_cells)` where `cols = max(len(row) for row in game_map)` and `total_cells = rows * cols`. `_handle_store_map` calls it on the raw source map; `_handle_count` calls it on the map *after* padding every row to `max_cols`, so `max(len(row))` over the padded rows equals the same `max_cols`. For the jagged `[['c4','c4','c4'], ['c4']]` both now report `rows=2, cols=3, total_cells=6` (previously `store_map` said 4, `count` said 6), verified by `test_jagged_map_dimensions_consistent_between_store_map_and_count`. The count answer stays 4 because padding inserts `'normal'`. The empty guard inside the helper (`... if game_map else 0`) is never exercised in production since both callers reject empty maps before calling it.

### Test isolation and the two new lock-in tests

`TestMemoryQuestion` now clears `_memory_store` in both `setUp` and `tearDown`, so `test_missing_game_map_error` asserts its empty-map error without depending on `TestMemoryMapRecall` sorting first — the order-coupling flagged in v1 is gone. `test_empty_passed_map_errors_even_when_map_remembered` seeds a map via `store_map`, then asserts a subsequent `count(game_map=[])` returns `error` and not `answer`, pinning exactly the contract that was ambiguous before. `test_jagged_map_dimensions_consistent_between_store_map_and_count` pins the reconciled dimensions and the unaffected count. Both new tests fail if their respective fixes are reverted, so they lock in behavior rather than restate it.

Not re-flagged: the prompt-only anti-loop. The Lambda is stateless per question and a genuine no-map error still returns a retryable 400 by design; loop prevention lives in the supervisor and memoryquestion prompts. v1 accepted this as appropriate and the follow-up documented it in the CHANGELOG v10 entry rather than changing code — consistent with the stateless architecture, so no action.
