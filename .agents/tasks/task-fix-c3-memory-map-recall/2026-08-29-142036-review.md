# Remember the game map so c3 Memory Trial counts stop looping (v1)

The c3 "Memory Trial" tile asks a counting question ("how many c4 challenges are on the map?") without re-sending the map, which is only shown once at game start for Pathfinding. Previously `count` demanded a `game_map`, returned `400 Missing game_map` when it got none, and the supervisor retried the same failing call ~9 times until the challenge failed and cost a life. This change remembers the map in the existing module-level `_memory_store` (warm-container = one game session): `lambda_handler` auto-persists any incoming non-empty `game_map` before dispatch, a new `store_map` action lets the supervisor stash the map explicitly at game start, and `_handle_count` falls back to the remembered map when the call omits one — failing cleanly with a descriptive 400 when no map exists anywhere. The prompts add the `store_map` tool, instruct storing the map at game start, tell `count` to omit the map, and add an anti-loop rule. Door/key transform logic is untouched and all 115 tests pass.

Watch for: (1) **confirmed** — an empty passed map (`game_map: []`) now silently falls back to the remembered map, which quietly changes the meaning of the existing `test_missing_game_map_error` and makes it order-dependent; (2) **confirmed** — the anti-loop guarantee lives entirely in the prompt, not the code, so the loop is only mitigated, not structurally prevented; (3) **likely** — `store_map` and `count` report different `total_cells` for jagged maps.

**Verdict**: NEEDS_CHANGES

## High-level view

The recall mechanism reuses the door-key store under a reserved `game_map` key and assumes warm-container lifetime maps to one game session. The main risk is not the happy path but the boundary between "no map passed" and "empty map passed": the code treats both as a fallback trigger, which changes the contract `count` previously had and makes an existing test pass only by luck of alphabetical class ordering.

The anti-loop fix — the actual point of the task — is delivered through prompt guidance ("do not repeat an identical failing call; answer 0 or move on"). The Lambda still returns a 400 when no map is available; nothing in the code prevents the supervisor from retrying. Whether the loop is actually gone depends on the model honoring the prompt, so the fix is a mitigation rather than a guarantee.

`store_map` and `count` disagree on `total_cells` for jagged maps because one measures the raw map and the other the padded map. The counted answer is correct either way; the confirmation number is inconsistent.

The recall tests would fail if the fix were reverted, but the suite leans on class-level `setUp`/`tearDown` clearing the shared store, and one pre-existing test in a class without that clearing is now silently coupled to the new behavior.

<summary>Details</summary>

### Recall over the shared door-key store

The map is remembered by writing `[list(row) for row in game_map]` under a reserved `GAME_MAP_KEY = 'game_map'` into the same `_memory_store` dict that holds door keys. The row-copy avoids aliasing the caller's list, and the reserved key coexists safely with door-key entries because door keys are named `door_key_*` and retrieval is by explicit key — there is no scan that would collide with `game_map`.

Auto-persist on every inbound non-empty map means a plain `count` that still carries a map (backward-compat path) also refreshes the remembered map, so the most recent real map always wins. `test_passed_map_takes_precedence_and_updates_remembered` pins this ordering, which is the subtle part worth locking down.

### Empty-map vs absent-map: a widened fallback trigger

`_handle_count` reads `game_map = body.get('game_map', [])` and then `if not game_map: game_map = _recall_map() or []`. Because `not []` is true, an explicitly passed empty map triggers the same recall fallback as a completely absent key. Before this change, `count` with `game_map: []` returned `400 Missing game_map`; now, if a map was remembered earlier in the session, that same call silently answers from the remembered map instead.

This is directly observable in the existing `test_missing_game_map_error`, which passes `game_map: []` and asserts an error. It passes today only because `TestMemoryMapRecall` sorts before `TestMemoryQuestion` and clears `_memory_store` in `tearDown`, leaving no remembered map when the older test runs. Seed a map first and the same call returns `answer` instead of `error`:

```
count(game_map=[], question="How many c1?")  with a map remembered  -> {"answer":"2", ...}
```

The fix should decide the contract deliberately: either an empty passed map is a caller error (distinguish `'game_map' not in body` from `game_map == []`), or empty-means-recall is intended and the old test should be updated to reflect it. Right now the behavior is incidental and the test is coupled to class execution order.

### Anti-loop is enforced in the prompt, not the code

The code contribution to stopping the loop is the clean fallback plus a more descriptive 400 (`No game_map available: none passed and none remembered from game start`). But a 400 is still a retryable outcome — nothing in the Lambda tracks that an identical call already failed, so the loop is only broken if the supervisor obeys the new prompt rule ("do not repeat an identical failing call — answer 0 or move on"), now present in both `supervisor_system_prompt.txt` and `memoryquestion_system_prompt.txt`. The Lambda is stateless per-question and can't know the challenge is failing, so loop prevention is best-effort model compliance, not a structural guarantee — worth naming so nobody assumes the code alone closes the loop.

### Jagged-map dimension reporting disagrees between paths

`_handle_store_map` computes `total_cells = sum(len(row) for row in game_map)` on the raw map, while `_handle_count` pads jagged rows to `max_cols` with `'normal'` before the same sum. For a jagged map like `[['c4','c4','c4'], ['c4']]`, `store_map` reports `total_cells=4` and a later `count` reports `total_cells=6`. The two also compute `cols` differently (`store_map` via `max(len(row) ...)`, `count` via `len(game_map[0])` after padding — agreeing here by coincidence). The counted answer is unaffected because padding uses `'normal'`, so this is a confirmation-number inconsistency, not a wrong count, and it only surfaces on non-rectangular maps.

### Test coverage

`TestMemoryMapRecall` is meaningful, not tautological: recall-from-`store_map`, recall-from-a-prior-`count`, the clean no-map-ever error, `store_map` returning dimensions without echoing the map, multi-type addition (c1+c8) against the recalled map, and passed-map-precedence-plus-remembered-update. Reverting the fallback in `_handle_count` breaks the two recall tests, and reverting auto-persist breaks the precedence test.

Not tested: the empty-passed-map-with-a-remembered-map case (the contract ambiguity above); jagged-map recall dimension consistency; and there is no test asserting `TestMemoryQuestion.test_missing_game_map_error` holds when a map is already remembered — the scenario that would expose the isolation problem.
